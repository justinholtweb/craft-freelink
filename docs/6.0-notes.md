# FreeLink 6.0 — Craft 6 port notes

The port implements `docs/5.3-design.md` on Craft 6.0.0-beta.1 + Laravel 13, with no
`craftcms/yii2-adapter`, no `yiisoft/yii2`, no `craft\`/`yii\` namespaces and no `Craft::`. These
are the decisions that differ from, or add to, the 5.3 design. Verified in the
`plugin-testing-craft6` harness (see `tests/README.md`).

## Field editor: Craft's own Ui controls, not custom JavaScript

FreeLink 5's input was Twig + Garnish/jQuery. Craft 6's CP is an Inertia/Vue app: a field returns a
Ui control from `uiControl()`, and the element editor renders and submits it through its own form
model. A vanilla custom element was considered and rejected: inputs it draws aren't part of the
Inertia form, so it would need its own serialisation into the form model, and it would have to
rebuild an element picker without `Craft.*` helpers.

Everything FreeLink needs exists as core controls:

- `Ui\Controls\Link` — Craft's link editor. It takes link types as plain config (`kind: text` with
  prefixes/pattern, or `kind: element` with an element select config), so FreeLink's types are
  passed in directly: url/email/phone/sms/custom as text kinds, site as one text type per site
  (`site:<id>`) on multi-site installs, entry/asset/user as element kinds with the field's sources
  and selection condition. Label, new window (`target`) and the advanced attributes map to the
  control's own fields.
- `Ui\Controls\Table` with `'control' =>` columns: one row per link. Multi-link mode allows
  add/delete/reorder and `minRows`/`maxRows`; single-link mode is one fixed row. An `IconPicker`
  column (free icons only unless `includeProIcons`) appears when icons are allowed; a `Textarea`
  column of `name=value` lines appears when advanced settings are on (the Link control has no
  custom attributes).

`Fields\LinkControl` converts between the control's value shape (`{type, value, label, target,
class, …}`, `{entry:12@1:url}` references, `mailto:`/`tel:`/`sms:` prefixes, email subject as
`?subject=`) and FreeLink's JSON. Posted rows are recognised by their `link` key, which stored JSON
and API input never have, so the field's stored format didn't change.

**Not verified in a browser.** The harness runs queued jobs from CP page views
(`runQueueAutomatically`) and other plugins' jobs were pending, so no CP page was opened in a
browser. The control payload, the posted shape and saving were verified server-side; how Craft's
Vue components render FreeLink's link type configs (prefix handling, patterns, the per-site types)
needs a visual check.

## Models, validation, events

- Links extend a small `Models\Model` over `CraftCms\Cms\Component\Component` (Caffeine's
  pattern): Laravel rules in `getRules()`, plus `checks()` for what a rule string can't say (unsafe
  URL schemes, attribute names, icons). Yii's URL and e-mail validator patterns are kept so the same
  values pass; a URL without a scheme still gets `https://` added on a successful validation.
- `RegisterLinkTypes` is a plain event class (`Event::listen`).
- Services are container singletons; `Plugin::getInstance()->links` etc. are kept as read-only
  property hooks.
- The field validates through `getElementRules()`. Craft 6 runs field rules in every scenario;
  FreeLink runs its full checks everywhere except `SCENARIO_ESSENTIALS` (draft saves), where only
  the security check runs (a new or changed element link must exist and be viewable by the user,
  or queryable by the GraphQL schema). Required is Craft's (layout element) via `isValueEmpty()`.
- `getLink()`/`getIconSvg()` return `HtmlString` (safe in Twig and Blade) instead of `Twig\Markup`.

## Sites

`ElementLink::resolvedSiteId()` — target site, else the owner's site (non-stored `ownerSiteId`,
set during normalisation), else the current site — is the one site a target is loaded on and every
visibility/scope check uses. Craft 6's element GraphQL resolvers don't apply a schema's
`sites.<uid>:read` scope in `prepareQuery()` (the query condition builder does, later), so
`GqlScope` enforces `GqlHelper::getAllowedSites()` itself. The harness has one site: the site scope
was verified with in-memory schemas without that site's scope, and the helper is unit-tested.

## Storage and migrations

- Tables, columns and JSON are unchanged. `Install.php` only creates missing tables, so 5.3 sites
  keep theirs. `m261119_000000_link_index_and_checks.php` keeps its Craft 5 name so it counts as
  applied. `$minVersionRequired = '5.3.0'`.
- `2026_11_19_000000_upgrade_to_craft_6.php` renames `justinholtweb\freelink\fields\FreeLinkField`
  in `fields.type` and project config (`Helpers\LegacyClassMap`, exact matches only; FreeLink 5
  stored no other class names), converts category links whose element is now an entry, and enables
  entry links on fields that enabled categories. Project config holds settings packed
  (`__assoc__`) while the `fields` table holds them unpacked; the migration reads and writes both
  forms. The legacy class strings (`justinholtweb\…`, `craft\elements\Category`/`Entry`) appear
  only as data.
- Field `dbType()` is `json`; values are a whole object/list per field.

## Migrators

Kept: **Craft's Link field**, rewritten for Craft 6 content (`elements_sites.content` keyed by
layout element UID; drafts and revisions converted too; field re-saved as a FreeLink field with the
same ID/UID/handle through `Fields::saveField()`, so project config follows). Dropped: **Hyper,
Linkit, Typed Link Field** — no Craft 6 versions, and FreeLink 5's migrators for them read Craft 4's
`content` table anyway. Their source names stay in the MCP enum and the commands so schemas match
5.3; running them explains that the migration has to happen on Craft 5.

Backups use `CraftCms\Cms\Database\Backups`; a failed backup stops the migration. A real run from
the CP needs a recently confirmed password (`ConfirmsPasswords`, Craft 6's elevated session).

## CP

- Links and Migrations are Twig partials in `CpScreenResponse::contentTemplate()` with plain HTML
  forms (`_includes/forms` is gone). Routes in `routes/cp.php` add `can:accessPlugin-freelink`,
  `can:freelink:viewLinks`/`checkLinks` and `RequireAdmin`/`RequireAdminChanges`.
- **Linked from** goes into `ElementMetadataResolving` (shown by both the Ui and the legacy editor);
  the Ui editor's `sidebarUi()` has no plugin hook.
- Sidebar label/icon/SVG are applied in `getCpNavItem()`; `Html::svg(sanitize: true, namespace:
  true)` on every draw. Craft 6's navigation customiser wins.

## Checks and queue

- `SsrfGuard`, `IpRanges`, the checker's redirect loop and `CurlTransport` (with
  `CURLOPT_RESOLVE` pinning, no proxy, http/https only) are ported unchanged apart from namespaces
  and dropping `curl_close()` (deprecated in PHP 8.5).
- Jobs extend `CraftCms\Cms\Queue\Job` / `BatchedJob` and go to the default queue, like Craft's
  own. 5.3 doesn't schedule checks, so neither does 6.0.
- Config-only `checkAllowedHosts`/`checkAllowedPorts` are read with `Config::get('craft.freelink.…')`
  every time and left out of `validationData()`, so a CP settings save can neither store nor apply
  them.

## Custom attributes

`UrlSafety::isSafeAttributeName()` is FreeNav's allowlist (identical to FreeLink 5.3.0's): plain attributes, `aria-*`, `data-*` minus framework directives. Values must be scalars. It's applied on save (`Link::checks()`), on render (`getSafeCustomAttributes()`, which skips stored unsafe attributes) and to MCP output; GraphQL input goes through the same validation, and GraphQL output doesn't expose custom attributes.

## Dropped

`LinkValidator` (unused Yii validator), `FreeLinkRecord` (ActiveRecord; replaced by the query
builder), the Craft 5 MCP polyfill, `gql/arguments` and `gql/resolvers` (unused in 5.3).
